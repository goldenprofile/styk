# Исходная идея: Orchestrator–Workers v1.0

Исходное предложение из обсуждения, структурированное для хранения. Его спорные гарантии разобраны в [следующем документе](02-architecture-review.md).

## Назначение

Минималистичная архитектура для соло-разработчика в небольшой компании. Приоритеты: скорость итераций, предсказуемость результата и сохранение контекста.

Четыре исходных принципа: Context Isolation, State-on-Disk / Blackboard, Deterministic Control Flow, Zero-Conflict Concurrency.

## 1. Два уровня

Supervisor — единственный агент, общающийся с человеком. Декомпозирует задачи, диспетчеризует исполнителей, принимает решения и синтезирует результат. Не читает длинные логи и не пишет код, кроме тривиальных правок менее десяти строк.

Workers — эфемерные узкоспециализированные исполнители с изолированным контекстом и урезанными инструментами. Не создают дочерних исполнителей. При нехватке данных возвращают `BLOCKED`.

## 2. Blackboard и тонкие указатели

Control Plane передаёт короткие сообщения управления. Data Plane хранит фактуру на диске:

```text
.agent-runs/<run_id>/
├── plan.json
├── artifacts/<task_id>.md
└── raw/<task_id>.log
```

`plan.json` содержит граф задач и статусы, Markdown — полный отчёт, лог — сырой вывод для диагностики. Следующий исполнитель получает путь и сам читает нужные разделы.

Ответ воркера предлагается ограничивать 1500 токенами:

```json
{
  "task_id": "t-02",
  "status": "SUCCESS",
  "summary": "Краткая суть результата в 3–5 предложениях",
  "artifacts": [".agent-runs/r-101/artifacts/t-02.md"],
  "changed_files": ["src/auth/token.ts"],
  "next_action_hint": "Готово к прогону тестов"
}
```

Допустимые статусы: `SUCCESS`, `FAILED`, `BLOCKED`.

## 3. Исполнение и конкурентность

Для read-only задач — in-process LLM sub-loops с отдельными `messages[]` и коротким системным промптом, ориентир около 300 токенов. Исходный текст заявляет нулевое время старта; это требует уточнения.

Для записи — отдельный процесс, при необходимости worktree. Read-only пул: до 4–6 задач в общей директории.

Запись выполняется либо последовательно в основном дереве (`concurrency = 1`), либо параллельно в `.agent-runs/<run_id>/wt-<task_id>/`. Затем — упорядоченный merge/cherry-pick и отдельное разрешение конфликтов. Параллельная запись в одну директорию запрещена.

## 4. ImplementAndVerify

Один макровызов оркестратора запускает автомат:

1. Coder реализует задачу.
2. Verifier без LLM запускает typecheck, lint и тесты.
3. При ненулевом exit code Fixer получает задачу, diff и последние 100 строк stderr.
4. После повторных ошибок повышается класс модели; после трёх попыток возвращается `FAILED`.

Исходное обозначение `MAX_RETRIES = 3` не уточняет, включён ли первый запуск. Заявлены переключение на reasoning после второй неудачи и остановка после третьей.

## 5. Пять ролей

| Роль | Класс модели | Инструменты | Результат |
|---|---|---|---|
| scout | Fast / Cheap | read, grep, find, git_log | Карта контекста в artifact.md |
| architect | Reasoning / Strong | read | План изменений в plan.json |
| builder | Balanced / Coding | read, write, edit, ограниченный bash | Реализация |
| verifier | Без LLM или Fast | Команды проверок | Результаты тестов, линтера, сборки |
| reviewer | Reasoning / Strong | read, git_diff | Конкретные замечания |

## 6. Маршрутизация моделей

Абстрактные классы `fast`, `workhorse`, `reasoning` сопоставляются моделям в едином конфиге. Исходное общее правило: повтор после `FAILED` или ошибки валидации повышает класс на одну ступень. Оно требует согласования с правилами ImplementAndVerify.

## 7. Наблюдаемость и управление

События `TASK_STARTED`, `TOOL_CALL`, `RETRY_ESCALATED`, `TASK_DONE` отображаются одной строкой на активного воркера.

Предлагается подтверждение человека перед builder, если план затрагивает более трёх файлов или меняет публичный контракт / схему БД.

Esc / Ctrl+C должны отменять исполнителей, сохранять состояние и позволять продолжить работу. Обещание мгновенной отмены и продолжения с места остановки требует отдельного протокола.

## 8. Этапы

1. Файловая шина, JSON-контракт, in-process scout и последовательный builder.
2. ImplementAndVerify, повторы и повышение класса модели.
3. Параллельные builders через worktree только при реальной необходимости.
