# Orchestrator–Workers v1.0

Предлагаемая спецификация. Поддержка Pi и переносимый интерфейс backend описаны в [дополнении](05-pi-integration.md).

## 1. Назначение и границы

Локальная система разработки изучает репозиторий, планирует изменения, реализует и проверяет их. Цели: скорость итераций, сохранение требований и доказательств, ограниченные расходы и понятное состояние после сбоя.

V1: один пользователь, один активный запуск на репозиторий и один writer. Параллельные worktree вводятся позже. Успешные тесты не доказывают полную корректность; отчёт содержит проверки и ограничения.

## 2. Компоненты

```text
Пользователь → Supervisor → Runtime → Workers
                              ├── состояние
                              ├── полномочия и диспетчеризация
                              ├── инструменты и проверки
                              └── бюджеты и отмена
```

Supervisor интерпретирует запрос, предлагает декомпозицию, разрешает содержательные развилки и отвечает пользователю.

Runtime — обычная программа, единственный владелец статусов и авторитетного плана. Запускает исполнителей, применяет политику повторов и принимает результаты.

Worker получает задание и собственный контекст. Не создаёт других воркеров и не меняет глобальный план. Два уровня агентного управления фиксированы; внутренние шаги запускает runtime.

## 3. Инварианты

1. Авторитетное состояние изменяет только runtime.
2. Проект одновременно изменяет максимум один исполнитель.
3. Результат связан с попыткой и состоянием проекта.
4. Опубликованные артефакты неизменяемы.
5. Вызовы и процессы имеют лимит времени.
6. Повторы ограничены попытками и общим бюджетом.
7. Репозиторий, логи и артефакты — данные, не источник новых полномочий.
8. Возобновление начинается со сверки состояния.

## 4. Задание

| Поле | Содержание |
|---|---|
| id | Идентификатор |
| objective | Требуемый результат |
| dependencies | Необходимые задачи |
| inputs | Требования и артефакты |
| acceptance_criteria | Наблюдаемые условия выполнения |
| capabilities | Разрешённые операции |
| verification_profile | Обязательные проверки |
| limits | Время, стоимость, попытки |

Пример критерия: истёкший токен возвращает HTTP 401; существующие сценарии авторизации проходят.

Изменение задания создаёт новую версию. Runtime помечает затронутые результаты для повторной оценки.

## 5. Хранилище

```text
.agent-runs/<run_id>/
├── request.md
├── state.json
├── events.jsonl
├── tasks/<task_id>/
│   ├── task.json
│   └── attempts/<attempt_id>/
│       ├── result.json
│       ├── report.md
│       ├── changes.patch
│       └── logs/
└── checkpoints/
```

`request.md` сохраняет запрос и уточнения. `state.json` — авторитетное состояние. `events.jsonl` — диагностика, а не единственный источник восстановления. Задание и результат содержат версии.

JSON и артефакты публикуются через временный файл и переименование. После аварии runtime сверяет состояние, результаты и рабочее дерево; неполная запись не означает успех.

Каталог запусков исключается из Git. Секреты по возможности редактируются в логах; сырые логи не передаются модели автоматически.

## 6. Контекст

Каждая попытка получает задание, критерии, инструкции репозитория, инструменты, ссылки на необходимые артефакты и исходный снимок проекта. Полная история Supervisor не копируется.

Большие отчёты читаются по разделам. Read-only роль может публиковать свой артефакт через runtime, но не изменять проект.

## 7. Роли

| Роль | Ответственность | Доступ |
|---|---|---|
| scout | Факты, зависимости, соглашения | Чтение |
| architect | Предложение плана и рисков | Чтение |
| builder | Реализация и исправления | Изменения и разрешённые команды |
| reviewer | Анализ diff и рисков | Чтение и diff |

Verifier — программный компонент для запуска проверок. Неоднозначную диагностику можно передать отдельной LLM-задаче. Минимум: scout, builder и verifier.

## 8. Жизненный цикл

```text
PENDING → READY → RUNNING → SUCCEEDED
                         → FAILED
                         → BLOCKED
                         → CANCELLED
```

`WAITING_APPROVAL` применяется при необходимости разрешения. `SUCCEEDED` означает подтверждение критериев предусмотренными проверками; `FAILED` — неуспех или исчерпание лимитов; `BLOCKED` — отсутствующее условие; `CANCELLED` — отмену.

Попытки учитываются отдельно: неуспех попытки может привести к повтору. Блокировка одной задачи не останавливает независимые задачи. Снятие блокировки и разрешение подтверждения выполняет runtime.

## 9. Результат попытки

```json
{
  "schema_version": 1,
  "run_id": "r-101",
  "task_id": "t-02",
  "attempt_id": "a-01",
  "outcome": "COMPLETED",
  "summary": "Добавлена проверка срока действия токена.",
  "reason_code": null,
  "input_snapshot_id": "s-014",
  "output_snapshot_id": "s-015",
  "artifact_refs": ["tasks/t-02/attempts/a-01/report.md"],
  "changed_files": ["src/auth/token.ts"],
  "verification": {
    "status": "PASSED",
    "check_refs": ["check-021", "check-022"]
  }
}
```

Outcomes: `COMPLETED`, `FAILED`, `BLOCKED`, `CANCELLED`. Runtime проверяет схему, ссылки, снимки и проверки. Заявление воркера не присваивает задаче `SUCCEEDED` автоматически. Пример транспортного лимита — 8 КиБ; подробности остаются на диске.

## 10. Исполнение и конкурентность

Read-only: отдельные сессии в одном процессе, начальный пул два вызова. Разведка завершается до записи. Writer получает исключительную блокировку репозитория.

До записи фиксируются commit при наличии, tracked и затрагиваемые untracked изменения, принадлежность правок пользователю или запуску. Пользовательские изменения не удаляются и не перезаписываются автоматически. Внешнее изменение затронутых файлов останавливает запись для переоценки.

Отдельный процесс используется по требованиям инструментов и изоляции; сам по себе он не считается sandbox.

## 11. ImplementAndVerify

```text
Предусловия → Builder → Проверки → Принятие результата
                           └── Ошибка кода → Исправление → Проверки
```

`max_attempts = 3` — три попытки всего, включая первую. Ошибка реализации передаётся builder; ошибка окружения вызывает ограниченное восстановление или блокировку; недостаточные требования возвращаются Supervisor; бюджет останавливает запуск; повтор без прогресса приводит к остановке или повышению tier.

Fixer получает задание, diff, структурированную диагностику и ссылки на полные логи. Проверки определяются профилем проекта: typecheck, lint, целевые тесты, сборка. Отсутствие проверок фиксируется явно.

## 12. Модели и бюджеты

`fast`: простая разведка. `workhorse`: реализация. `reasoning`: сложное проектирование, диагностика и ревью.

Центральный конфиг сопоставляет классы конкретным моделям и требуемым возможностям. Повышение класса связано с содержательной ошибкой модели или отсутствием прогресса. Ошибка сети или прав не повышает модель автоматически.

Лимиты: длительность запуска и команды, попытки, вызовы инструментов, стоимость при доступном учёте. Повторы и эскалация расходуют общий бюджет.

## 13. Полномочия и подтверждения

Разрешённые пути, передача окружения, сеть, команды и тайм-ауты задаются явно. Тесты также исполняют код проекта и подчиняются ограничениям.

Подтверждение зависит от действия и уже данной авторизации, не от числа файлов. Удаление данных, публикация и применение миграций к рабочей базе могут требовать отдельного решения. Подготовка и фактическое внешнее действие разделены.

## 14. Наблюдаемость и восстановление

Событие содержит время, run/task/attempt ID, тип и короткие данные. Типы: `TASK_STARTED`, `TOOL_STARTED`, `TOOL_FINISHED`, `CHECK_FINISHED`, `RETRY_SCHEDULED`, `TASK_BLOCKED`, `TASK_FINISHED`, `RUN_CANCELLED`.

Интерфейс показывает шаг, длительность, попытку, tier и последнее значимое событие.

Отмена прекращает диспетчеризацию, сигнализирует операциям, ограниченно ждёт и завершает управляемые процессы, сохраняет данные и помечает незавершённые попытки.

Возобновление сверяет проект, артефакты и операции. Продолжение — с подтверждённой точки; внешние действия не повторяются вслепую.

## 15. Этапы

1. Полный вертикальный сценарий: scout, последовательный builder, состояние, проверки, лимиты, отмена. Готовность: успех, ошибка и отмена оставляют проверяемый результат.
2. ImplementAndVerify, классификация, повторы, routing, reviewer. Готовность: типовая ошибка исправляется, окружение отделяется от кода, лимит останавливает цикл.
3. Worktree, изоляция ресурсов проверок, последовательная интеграция и общая проверка. Вводить, когда измерения подтверждают ожидание независимых задач из-за занятого builder.
