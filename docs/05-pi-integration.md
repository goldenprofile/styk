# Использование системы в Pi Coding Agent

Дополнение к [спецификации v1.0](03-stykpecification.md). Архитектурный проект интеграции; реализация Supervisor-инструментов и установка через `styk install-pi` описаны в [README](../README.md#цель-в-чате-pi-вместо-ручного-json). Не все возможности из этого документа реализованы. Документация проверена 2026-11-13; установленная у пользователя версия Pi пока неизвестна.

## 1. Что подтверждено

Pi предоставляет SDK для встраивания в Node.js/Bun. `createAgentSession()` создаёт отдельную сессию; доступны сообщения, модель, инструменты, события и управление хранением. SDK использует ресурсы и настройки среды, поэтому их загрузку следует контролировать явно. [Pi SDK](https://pi.dev/docs/latest/sdk)

RPC запускает Pi как долгоживущий дочерний процесс с JSONL-командами и событиями. Ответ команды означает обработку команды; завершение агентной работы определяется событиями жизненного цикла. Интерфейс установленной версии уточняется через `pi --help`. [Pi RPC](https://pi.dev/docs/latest/rpc)

Extensions поддерживают регистрацию инструментов, команд, события и элементы интерфейса. Это точки подключения нашего workflow к терминальному Pi. [Pi Extensions](https://pi.dev/docs/latest/extensions)

Официальный сайт описывает subagents и plan mode как функциональность, которую можно добавить расширениями. Следовательно, роли и scheduler нашей системы следует реализовать явно. [Pi](https://pi.dev/)

## 2. Два способа использования

### Pi как исполнитель

```text
Supervisor → Общий runtime → Pi adapter → Worker session
```

Runtime создаёт отдельную Pi-сессию для задания, выбирает модель, выдаёт инструменты, собирает результат и запускает независимые проверки.

### Pi как пользовательская среда

```text
Пользователь → Pi TUI → Styk extension → Общий runtime
                                           ├── Pi adapter
                                           ├── Codex adapter
                                           └── Claude adapter
```

Расширение предоставляет команды запуска, просмотра статуса и отмены. Диалоговая сессия Pi выполняет роль Supervisor, а рабочие сессии получают отдельный контекст. Хранение и переходы остаются в ядре.

Эти режимы совместимы: пользователь работает в Pi, а runtime выбирает поддерживаемый backend исполнителя.

## 3. Рекомендуемая структура

```text
src/
├── core/
│   ├── contracts.ts
│   ├── scheduler.ts
│   ├── state-store.ts
│   ├── artifact-store.ts
│   ├── workspace-lock.ts
│   ├── verifier.ts
│   ├── budgets.ts
│   └── cancellation.ts
├── adapters/
│   ├── pi.ts
│   ├── codex.ts
│   └── claude.ts
└── integrations/
    └── pi-extension.ts
```

Это предложенный layout. `core` не импортирует SDK поставщиков. UI не записывает `state.json` напрямую. Runtime остаётся единственным владельцем состояния независимо от интерфейса.

## 4. Переносимый контракт backend

Эскиз собственного интерфейса; не API Pi:

```ts
type ExecutionBackend = "pi" | "codex" | "claude";
type ModelTier = "fast" | "workhorse" | "reasoning";

interface WorkerRequest {
  runId: string;
  taskId: string;
  attemptId: string;
  workspace: string;
  inputSnapshotId: string;
  taskFile: string;
  artifactRefs: string[];
  tier: ModelTier;
  capabilities: string[];
  timeoutMs: number;
}

interface BackendCapabilities {
  independentSessions: boolean;
  toolAllowlist: boolean;
  structuredOutput: boolean;
  cooperativeAbort: boolean;
  hardProcessTermination: boolean;
  filesystemSandbox: boolean;
}

interface WorkerBackend {
  capabilities(): Promise<BackendCapabilities>;
  execute(
    request: WorkerRequest,
    signal: AbortSignal,
    emit: (event: RuntimeEvent) => void,
  ): Promise<WorkerResult>;
}
```

`RuntimeEvent` и `WorkerResult` определяются схемами ядра. Флаги отражают фактический выбранный режим и внешнюю sandbox, а не бренд продукта. Недоступная обязательная возможность вызывает ошибку до начала исполнения.

## 5. Выбор транспорта

| Режим | Применение | Ограничение |
|---|---|---|
| SDK, отдельная сессия | Read-only разведка с низким overhead | Общий процесс не является границей безопасности |
| RPC, дочерний процесс | Builder и задачи, требующие принудительного завершения | Процесс сам по себе не ограничивает файловый доступ |
| Extension | Команды и статус внутри Pi | Не дублирует scheduler и state store |

Для первого прототипа: SDK для scout, RPC для builder. Если поддержка двух транспортов задерживает полный сценарий, допустимо временно использовать RPC для обоих с явным ограничением производительности.

## 6. Контекст и инструменты

Создавать новую сессию на попытку; не копировать историю Supervisor. Передавать задание, инструкции, критерии, ссылки на доказательства и снимок.

Scout получает только контролируемое чтение и поиск плюс публикацию отчёта. Builder получает запись в согласованной области и команды через контролируемый executor. Не подключать автоматически все пользовательские extensions и MCP-инструменты в рабочие сессии.

Проверить на закреплённой версии, что загрузчик ресурсов и выбранный режим действительно исключают неразрешённые инструменты. Наличие `bash` делает read-only ограничение недостаточным без отдельного контроля.

## 7. Результат и модель

Runtime предоставляет инструмент публикации результата с собственной схемой. Он проверяет данные, пути и принадлежность артефактов; финальный текст сессии используется как пояснение. При отсутствии валидной публикации попытка не принимается.

Backend исполнения и provider модели — разные настройки. Pi может использовать модель OpenAI или Anthropic, но это не запускает Codex harness или Claude Code harness.

Пример проектной конфигурации:

```json
{
  "schema_version": 1,
  "default_backend": "pi",
  "writer_concurrency": 1,
  "max_attempts": 3,
  "tiers": {
    "fast": { "provider": "CONFIGURE_ME", "model": "CONFIGURE_ME" },
    "workhorse": { "provider": "CONFIGURE_ME", "model": "CONFIGURE_ME" },
    "reasoning": { "provider": "CONFIGURE_ME", "model": "CONFIGURE_ME" }
  }
}
```

Имена моделей выбираются после проверки доступных пользователю providers. Секреты не входят в конфиг проекта. Автоматическая смена backend при ошибке в v1 отключена: она может изменить окружение и полномочия.

## 8. Интерфейс в Pi

Предлагаемые команды расширения, пока не существующие:

- `/styk-run <задача>` — создать запуск.
- `/styktatus` — задачи, попытки, проверки, бюджет.
- `/styk-cancel` — отменить операции runtime.
- `/system-resume <run_id>` — сверить состояние и продолжить.

Проектируемый инструмент `system_dispatch` позволяет Supervisor передать задание runtime. Обычные команды, вызов инструмента и UI используют один сервис ядра.

Отмена привязывается к механизму прерывания текущей версии Pi и явной команде. Нельзя обещать, что обычное прерывание главной сессии автоматически завершает созданные расширением процессы: это отдельная обязанность интеграции.

## 9. Восстановление

Сохранять ссылку на Pi-сессию при доступном persistent storage и собственные attempt/snapshot ID. Сессия Pi не заменяет состояние workflow.

После рестарта сначала сверить дерево и незавершённые операции. Затем либо продолжить совместимую сессию, либо создать новую с заданием и артефактами. Непроверенный промежуточный diff не становится принятым результатом.

## 10. План первого этапа

1. Проверить установленный Pi и его версию, закрепить совместимый SDK. В этой сессии установка не выполнялась.
2. Реализовать схемы, state/artifact store и блокировку записи.
3. Добавить Pi backend и одну scout-задачу.
4. Подключить последовательный builder и независимый verifier.
5. Обеспечить отмену, тайм-ауты и сверку при возобновлении.
6. Добавить тонкое расширение Pi с командами и статусом.
7. После полного сценария подключать Codex и Claude адаптерами.

На момент проверки официальная документация использует пакет `@earendil-works/pi-coding-agent`. Старые примеры могут использовать другое имя; не смешивать импорты и протоколы разных поколений.

## 11. Критерии готовности

- Из Pi можно запустить задачу и получить проверенный отчёт.
- Scout не может изменить проект или вызвать нового исполнителя.
- Два запроса builder не получают одновременный доступ на запись.
- Ошибка проверки вызывает ограниченный повтор, ошибка доступа — блокировку.
- Отмена останавливает управляемые процессы и сохраняет состояние.
- После рестарта изменения пользователя обнаруживаются до новой записи.
- Диалог, сессии воркеров и состояние runtime не смешиваются.
- Адаптер другого backend не требует изменения схем ядра.
