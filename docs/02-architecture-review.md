# Разбор исходной архитектуры

## Оценка

Основа разумна: изоляция контекста, файловые доказательства, последовательная запись и программные проверки. Для исполняемой спецификации недостаёт владения состоянием, согласованности публикации, критериев успеха и протокола восстановления.

## Сильные решения

- Два уровня ограничивают расходы и сложность диагностики.
- Короткие управляющие ответы сохраняют внимание Supervisor.
- Артефакты удерживают исходные факты и доказательства.
- Один writer уменьшает затраты на интеграцию.
- Счётчики попыток и ветвления в коде не зависят от памяти модели.
- Worktree отложены до появления измеримой потребности.

## Завышенные гарантии

| Заявление | Корректная граница |
|---|---|
| Отсутствие деградации контекста | Изоляция уменьшает загрязнение, но требует передачи требований и связей |
| Старт за 0 мс | Нет запуска отдельного процесса, но остаются подготовка и задержка модели |
| Zero-Conflict | Worktree разделяют файлы; интеграционные и логические конфликты остаются |
| Детерминированный pipeline | Детерминированы переходы; генерация и некоторые проверки могут различаться |
| Атомарный pipeline | Один вызов не откатывает частичные изменения |
| Мгновенная отмена | Сигнал отправляется сразу; завершение требует времени |

## Владение состоянием

Read-only architect не может напрямую писать `plan.json`; scout с теми же правами не может публиковать файл обычным write. Следует разделить изменения проекта и публикацию служебного результата.

Только runtime меняет авторитетный план и статусы. Архитектор предлагает план, runtime проверяет и сохраняет. Воркеры публикуют результаты через выделенный инструмент.

## Согласованность Blackboard

Для каждой попытки нужны собственный идентификатор, неизменяемые опубликованные артефакты и безопасная запись через временный файл с переименованием. Перед принятием результата runtime проверяет ссылки и полноту публикации.

Результат связывается с состоянием проекта. Commit SHA недостаточен при незакоммиченных изменениях: необходим снимок соответствующего рабочего дерева. Следует определить поведение после сбоя между записью отчёта, результата и обновлением статуса.

## Контракты и статусы

Добавить `schema_version`, `run_id`, `attempt_id`, `reason_code`, результаты проверок и исходную ревизию / снимок. `next_action_hint` — рекомендация, не команда.

Токены не переводятся в байты с постоянным коэффициентом. Транспортный лимит лучше задавать в байтах и длинах полей.

Разделить состояния `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `BLOCKED`, `CANCELLED`; для подтверждений добавить `WAITING_APPROVAL`. У блокировки должны быть причина и условие снятия. Попытка и задача — разные сущности.

## Проверки, повторы и эскалация

Exit code 0 означает успешное выполнение выбранных проверок, но не полное выполнение требований. Нужны наблюдаемые критерии приёмки.

Классифицировать сбои: ошибка кода, окружения, доступа, требований, нестабильной проверки. Повышать модель только там, где поможет дополнительное рассуждение.

Согласовать правила повышения класса. Использовать `max_attempts = 3` для трёх попыток всего. Диагностика должна включать stdout, stderr, команду, exit code и ссылки на полный вывод: последние 100 строк stderr часто недостаточны.

## Полномочия

Процесс и worktree не ограничивают автоматически сеть, секреты и остальную файловую систему. «Ограниченный bash» требует конкретной политики и механизма исполнения. Verifier запускает код проекта и также нуждается в ограничениях.

## Конкурентность

Read-only воркер может получить несогласованную картину, если builder одновременно меняет файлы. В v1 разведка завершается до записи; позже вводится чтение закреплённых снимков.

Worktree не разделяют порты, базы, внешние сервисы и все кэши. После интеграции нужна повторная проверка объединённого результата.

## Отмена и восстановление

Определить остановку дочерних процессов, тайм-аут корректного завершения, статус прерванной попытки, проверку файлов и правила повторяемости операций.

Продолжать с подтверждённой контрольной точки после сверки состояния. Не обещать продолжение из произвольной середины LLM-вызова или автоматический повтор внешнего действия.

## Минимальное ядро

Единственный владелец состояния, scout, последовательный builder, схемы сущностей, безопасная публикация, критерии приёмки, лимиты и отмена. Architect и reviewer сначала достаточно представить профилями вызова. Масштабирование обосновывать длительностью задач, ценой повторов и временем интеграции.
